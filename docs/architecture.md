# PersonaForge: архитектура

## Задача

Сделать так, чтобы новый бот был описанием, а не новой папкой с обработчиками. Сценарий, экраны и собираемые поля должны лежать рядом, проверяться вместе и не требовать правок движка.

## Три части определения

| Часть | Что описывает | Что не знает |
| --- | --- | --- |
| `fsm` | состояния и переходы по событиям | про текст, кнопки и форму |
| `viewMap` | экран для каждого состояния | про переходы и валидацию |
| `form` | поля, типы, defaults, required | про состояния и экраны |

`BotPersona` — агрегат, который связывает их и проверяет инварианты. Это единственное место, где встречаются все три части.

## Почему данные, а не код

Плюсы:

- сценарий можно прочитать целиком, не переходя по импортам;
- новый бот не требует нового класса;
- определение можно сохранить в БД и версионировать;
- тесты проверяют данные, а не побочные эффекты.

Минусы:

- типы полей проверяются в рантайме;
- сложную логику (расчёты, внешние API) в `assign` не положить;
- для нестандартного экрана нужен новый компонент, а не просто текст.

Компромисс: движок остаётся маленьким, а всё, что требует кода, выносится в адаптеры и компоненты.

## Переход

`Conversation.process()` делает переход атомарно:

1. находит переход по событию;
2. создаёт копию формы (или новую форму при `resetForm`);
3. применяет `assign` в копию;
4. только после успеха меняет состояние, форму и историю.

Если payload неполный или значение не того типа, возвращается `{ ok: false, reason }`, а диалог остаётся на месте. Частично применённых переходов нет.

## Инварианты

- `initialState` существует;
- все цели переходов существуют;
- id состояний уникальны;
- у каждого состояния есть экран;
- у каждого экрана есть состояние;
- `assign` пишет только в существующие поля;
- литерал совпадает с типом поля;
- `{{поле}}` в тексте существует в форме;
- кнопка отправляет событие, которое есть из этого состояния.

## Слои

```text
domain/         FSM, ViewMap, Form, BotPersona, Conversation
application/    engine, use cases, ports
infrastructure/ in-memory repositories
rendering/      renderMessage, toTelegram
examples/       три определения
demo/           сценарный прогон
```

Домен не импортирует Telegram. Рендер не импортирует репозитории. `engine.ts` — единственная точка сборки.

## Хранилище

Контракты:

```ts
interface PersonaRepository {
  save(persona: BotPersona): Promise<void>;
  findById(id: string): Promise<BotPersona | null>;
}

interface ConversationRepository {
  save(conversation: Conversation): Promise<void>;
  findActiveByChatId(chatId: string): Promise<Conversation | null>;
}
```

Для Postgres достаточно сохранить `definition` как JSON, а `Conversation` — как строку состояния, JSON формы и историю. Домен для этого менять не нужно.

## Что не вошло

- Транспорт Telegram: polling, webhook, `callback_query`, текст как событие.
- Медиа-компоненты.
- Локализация.
- Версионирование определений и миграции.
- Аналитика воронки.
- Конкурентность и блокировки.

Это следующие шаги, а не скрытая часть текущей версии.
